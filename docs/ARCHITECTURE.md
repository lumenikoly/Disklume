# Архитектура

## Границы ответственности

У приложения три слоя: независимое от окна файловое ядро, тонкая оболочка Tauri и пользовательский интерфейс. Ядро не вызывает JavaScript, не знает о Canvas, HTML и состоянии панелей. Интерфейс не получает произвольный доступ к файловой системе.

```text
App (контроллер интерфейса)
 ├── FileMap → чистый buildLayout → Canvas
 └── Backend
      ├── NativeBackend → типизированные команды Tauri → Engine
      └── DemoBackend → только данные в памяти

Engine
 ├── Session / Index
 ├── scanner
 ├── query / make_nodes
 ├── duplicates
 └── operations → TrashProvider
                  ├── Windows IFileOperation
                  ├── Linux GIO
                  ├── macOS trash
                  └── TestTrash в тестах
```

Синтетический Backend используется только локальными UI-тестами, чтобы проверять интерфейс без настоящих файлов; пользовательского режима-примера нет. Это не абстрактная система подключаемых хранилищ. Единственная подменяемая системная операция ядра — TrashProvider: она позволяет проверить безопасную последовательность действий без реальной Корзины.

## Сессия и потоки

Выбор папки создаёт новый scanId и Arc<Session>. Session содержит Mutex<Index> и атомарный флаг остановки. Engine имеет общий mutation-замок: смена сессии, переход к фоновой операции и изменения плана не могут конкурировать между собой. Проверка устаревшего scanId выполняется после захвата этого замка для изменяющих операций. Отмена диалога выбора не меняет текущую сессию; новая сессия подменяет старую только после проверки пути, корня и доступности чтения. При повторном сканировании корень берётся из текущей сессии, поэтому невыполненный или отклонённый rescan оставляет прежний план и индекс.

Рабочая задача выполняет обход, поиск дубликатов или перенос в Корзину. Одновременно у сессии одна такая задача. При обходе до восьми ограниченных рабочих потоков читают разные каталоги; каталоги попадают в очередь только после проверки типа, reparse/symlink-признаков, границы файловой системы и глубины. Результаты идут через ограниченный канал, а единственный поток добавляет их в индекс пачками по 256 элементов или примерно раз в 120 мс. Поэтому `fileId`, счётчики жёстких ссылок и ревизии индекса остаются сериализованными. Mutex индекса не удерживается во время чтения содержимого, записи журнала или вызова Корзины. Полный запрос на фильтрацию и сортировку выполняется под замком индекса, но в блокирующем рабочем потоке Tauri, не в потоке окна.

Допустимые состояния: scanning, ready, cancelled, hashing, deleting, failed. План меняется только вне активной фоновой операции. Остановка кооперативная: обход — между записями, хеширование — между блоками, удаление — между отдельными вызовами ОС. Уже начатый системный перенос прервать в середине нельзя. Закрытие окна во время переноса блокируется с объяснением.

## Индекс

В Rust находятся нативные относительные PathBuf, идентичность и метаданные файла. fileId — индекс записи в векторе в пределах текущей сессии; он никогда не используется без scanId. Удалённые записи помечаются, но их позиции не переиспользуются. После повторного сканирования прежние идентификаторы перестают быть действительными.

Логический размер суммируется по путям. Выделенное место учитывается один раз для одной файловой идентичности, поэтому жёсткие ссылки не умножают физический объём. После успешных действий счётчики пересчитываются. Это оценка размещения, не «объём, который освободится».

Пути преобразуются в строки только для текущего набора отображения, карточки и сообщений. Потеря точного представления редких не-UTF8 имён не превращает отображаемую строку в полномочие на удаление: операция всё равно использует исходный PathBuf по ID.

## Запрос и ограничение сцены

query фильтрует индекс, сортирует ссылки на записи по убыванию выбранного размера, возвращает страницу из 200 файлов. Для карты выбираются 480 крупных файлов; остальное агрегируется по типу, давности и признаку скриншота. Таким образом объём сцены не растёт пропорционально миллиону записей индекса.

У группы есть диапазон курсоров after..through = (bytes, id). При раскрытии выбираются только записи внутри этого диапазона и в соответствующей категории. Большие однородные остатки делятся в пределах фиксированного бюджета групп, поэтому раскрытие не снимает по 480 файлов за клик. Без границ та же группа могла бы повторять уже показанные крупные файлы. Сумма площадей и количеств групп соответствует отфильтрованному набору.

Нынешняя сложность запроса — O(N log N) для сортировки и O(N) для фильтра. Это сознательно простая реализация. Собственные индексы для каждого фильтра и фоновые снимки нужно вводить только после профилирования на реальных больших каталогах. Скорость на миллионе реальных файлов в этой поставке не измерялась.

## Геометрия

buildLayout — чистая детерминированная функция. Радиус равен sqrt(bytes / maxBytes) × 100. Крупные круги размещаются первыми, начиная с центра; остальные упаковываются без пересечений. Возраст не влияет на координаты. Пространственная сетка ускоряет проверку пересечений. Пустые файлы получают нулевую площадь и отдельную область попадания мыши.

Дубликаты соединяются линиями. В обзорном масштабе крупнейшие файлы получают выносные подписи. После изменения набора раскладка может измениться; постоянных координат на диске нет.

## Навигация по папкам

Индекс хранит каталоги с ID, стабильными внутри scanId; корень имеет ID 0. Интерфейс запрашивает directoryId через query_view, а не передаёт путь. Режим folders агрегирует подходящие файлы по непосредственным дочерним каталогам, добавляет файлы текущего уровня и возвращает до 200 записей по убыванию размера. Размеры и доли относятся к выбранной метрике и действующим фильтрам. Без фильтров отображаются также пустые каталоги. Полное дерево не передаётся в интерфейс.

Путь для возврата состоит из названий и ID каталогов. Каталоги доступны для навигации и показа в системном файловом менеджере по паре `scanId + directoryId`; перед показом ядро заново проверяет корень и каждый компонент каталога. Открытие и удаление файлов используют только `fileId`. После удаления выбранных файлов запрос пересчитывает размеры всех предков; directoryId сохраняется до нового сканирования.

Canvas перерисовывается по событию через requestAnimationFrame: данные, движение, масштаб, выделение, размер окна. Постоянного цикла физики или анимации нет. Компоненты DOM отвечают за панели, кнопки, таблицу и диалоги. В обычном списке доступны те же действия, что на карте.

## Обмен с оболочкой

Имена команд собраны в src-tauri/build.rs и явном разрешении commands.toml. Граница frontend/Rust описана в src/types.ts. Общих разрешений для файловой системы, оболочки или произвольного системного открытия в JavaScript нет. Плагин открытия вызывается только из Rust после проверки файловой записи.

Статус опрашивается раз в 500 мс только во время активной задачи. Запросы вида объединяются, а ответы устаревшего поколения игнорируются. Для изменения файлов используется отдельная сериализованная цепочка действий интерфейса, но окончательные проверки остаются в Engine.

## Дубликаты

Сначала рассматриваются только ненулевые файлы одинакового размера с разной идентичностью. В промежуточной группировке хранятся ID, а не копии всего индекса. Для текущей группы берётся выборка по 16 КиБ в начале, середине и конце. Одинаковые выборки ещё не означают дубликат: необходим полный BLAKE3. Чтение последовательное, по 256 КиБ, с возможностью остановки. Сигнатура метаданных проверяется перед чтением, после чтения и перед публикацией группы.

## Удаление

План — набор fileId с ограничением 10 000 и монотонной planRevision. Подтверждение содержит ревизию увиденного пользователем плана. Backend отклоняет устаревшее подтверждение. Перед каждым вызовом ОС: проверка → синхронная запись намерения в журнал → повторная проверка → Корзина → запись результата. Неуспешный пункт остаётся в плане. Никаких фоновых повторных попыток после перезапуска нет.

Windows использует отдельный небольшой модуль COM с явным FOFX_RECYCLEONDELETE и запретом связанного перемещения HTML-папок. Linux использует GIO trash, macOS — адаптер trash. Единственный разрешённый unsafe-код самого проекта находится в модуле Windows COM и документирует время жизни буфера и COM-потока. Остальные модули запрещают unsafe на уровне предупреждения deny.

## Почему без React, PixiJS и базы

При таком количестве экранов отдельная система компонентов и хранилище состояния увеличили бы объём связующего кода. Для ограниченной сцены Canvas достаточен; это подтверждено тестами геометрии и браузерной проверкой, но не является доказательством производительности на любой машине. SQLite, постоянный индекс и наблюдатель файловой системы не нужны для одного явно выбранного сеанса уборки.
