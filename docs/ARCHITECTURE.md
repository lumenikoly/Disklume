# Архитектура

## Границы ответственности

У приложения три слоя: независимое от окна файловое ядро, тонкая оболочка Tauri и пользовательский интерфейс. Ядро не вызывает JavaScript, не зависит от HTML и состояния панелей. Интерфейс не получает произвольный доступ к файловой системе.

```text
App (контроллер интерфейса)
 ├── treemap → ограниченные DOM-прямоугольники + список текущей страницы
 └── Backend
      ├── NativeBackend → типизированные команды Tauri → Engine
      └── DemoBackend → только данные в памяти

Engine
 ├── Session / Index
 ├── scanner
 ├── query_view
 └── operations → TrashProvider
                  ├── Windows IFileOperation
                  ├── Linux GIO
                  ├── macOS trash
                  └── TestTrash в тестах
```

Синтетический Backend используется только локальными UI-тестами, чтобы проверять интерфейс без настоящих файлов; пользовательского режима-примера нет. Это не абстрактная система подключаемых хранилищ. Единственная подменяемая системная операция ядра — TrashProvider: она позволяет проверить безопасную последовательность действий без реальной Корзины.

## Сессия и потоки

Выбор папки создаёт новый scanId и Arc<Session>. Session содержит Mutex<Index> и атомарный флаг остановки. Engine имеет общий mutation-замок: смена сессии, переход к фоновой операции и изменения плана не могут конкурировать между собой. Проверка устаревшего scanId выполняется после захвата этого замка для изменяющих операций. Отмена диалога выбора не меняет текущую сессию; новая сессия подменяет старую только после проверки пути, корня и доступности чтения. При повторном сканировании корень берётся из текущей сессии, поэтому невыполненный или отклонённый rescan оставляет прежний план и индекс.

Сканирование и перенос в Корзину выполняются рабочими задачами. Одновременно у сессии одна такая задача. При обходе до восьми ограниченных рабочих потоков читают разные каталоги; каталоги попадают в очередь только после проверки типа, reparse/symlink-признаков, границы файловой системы и глубины. Результаты идут через ограниченный канал, а единственный поток добавляет их в индекс пачками по 256 элементов или примерно раз в 120 мс. Поэтому `fileId`, счётчики жёстких ссылок и ревизии индекса остаются сериализованными. Mutex индекса не удерживается во время чтения содержимого, записи журнала или вызова Корзины. Полный запрос на фильтрацию и сортировку выполняется под замком индекса, но в блокирующем рабочем потоке Tauri, не в потоке окна.

Допустимые состояния: scanning, ready, cancelled, hashing, deleting, failed. План меняется только вне активной фоновой операции. Остановка кооперативная: обход — между записями, удаление — между отдельными вызовами ОС. Уже начатый системный перенос прервать в середине нельзя. Закрытие окна во время переноса блокируется с объяснением.

## Индекс

В Rust находятся нативные относительные PathBuf, идентичность и метаданные файла. fileId — индекс записи в векторе в пределах текущей сессии; он никогда не используется без scanId. Удалённые записи помечаются, но их позиции не переиспользуются. После повторного сканирования прежние идентификаторы перестают быть действительными.

Логический размер суммируется по путям. Выделенное место учитывается один раз для одной файловой идентичности, поэтому жёсткие ссылки не умножают физический объём. После успешных действий счётчики пересчитываются. Это оценка размещения, не «объём, который освободится».

Пути преобразуются в строки только для текущего набора отображения, карточки и сообщений. Потеря точного представления редких не-UTF8 имён не превращает отображаемую строку в полномочие на удаление: операция всё равно использует исходный PathBuf по ID.

## Запрос и ограничение страницы

Интерфейс вызывает query_view в режиме folders с метрикой allocated и ID текущего каталога. Ядро применяет поиск к вложенным файлам, суммирует размеры непосредственных дочерних папок и возвращает смешанную страницу каталогов и файлов, отсортированную по убыванию размера. На странице до 200 объектов; полный индекс остаётся в Rust.

Карта использует ту же страницу. Размер объектов остальных страниц представляется одним агрегатным прямоугольником. Общий объём, количество файлов, число объектов страницы и путь для возврата приходят в одном ответе. После переноса файлов в Корзину ядро пересчитывает суммы папок.

Сложность запроса — O(N log N) для сортировки и O(N) для поиска. Индексы поиска и фоновые снимки следует вводить после измерений на реальных больших каталогах. Скорость на миллионе реальных файлов не измерялась.

## Геометрия и интерфейс

Основной интерфейс всегда запрашивает folders с метрикой allocated. Один экран содержит прямоугольную карту, список текущего уровня и поиск по имени/пути.

Чистая функция treemap строит детерминированную squarified-раскладку. Площадь прямоугольника пропорциональна bytes. Отображаются до 200 объектов текущей страницы плюс один прямоугольник для суммарного размера остальных страниц. Он открывает следующую страницу; на последней — первую. Полная сумма размеров берётся из query_view, поэтому маленькая страница не выглядит как вся папка. Объекты нулевого размера остаются в списке без искусственной площади на карте.

Прямоугольники — обычные кнопки DOM с доступными именами. Нажатие на папку открывает её содержимое; файл выделяется одновременно на карте и в списке. Панель выбранного файла содержит имя, размер, путь и действия открыть / показать / Корзина. ResizeObserver пересчитывает геометрию при изменении размеров контейнера. Перерисовка выполняется при изменении данных, выделения или размеров контейнера.

«В Корзину…», Delete и соответствующий пункт контекстного меню добавляют индивидуальные fileId в план и сразу открывают его проверку. План исполняется только с подтверждённой ревизией. После отмены появляется небольшая строка для возврата к плану или его сброса.

## Навигация по папкам

Индекс хранит каталоги с ID, стабильными внутри scanId; корень имеет ID 0. Интерфейс запрашивает directoryId через query_view, а не передаёт путь. Режим folders агрегирует подходящие файлы по непосредственным дочерним каталогам, добавляет файлы текущего уровня и возвращает до 200 записей по убыванию размера. Размеры и доли относятся к выбранной метрике и действующим фильтрам. Без фильтров отображаются также пустые каталоги. Полное дерево не передаётся в интерфейс.

Путь для возврата состоит из названий и ID каталогов. Кнопки назад/вперёд/выше и Alt+←/→/↑ работают по истории до 100 посещений; поиск, страница и прокрутка восстанавливаются. Новый переход очищает поиск и обрезает ветку вперёд. Смена scanId сбрасывает историю; после переноса папки история её поддерева удаляется и открывается сохранившийся родитель. Каталоги доступны для навигации и показа в системном файловом менеджере по паре `scanId + directoryId`; перед показом ядро заново проверяет корень и каждый компонент каталога. Открытие и удаление файлов используют только `fileId`. Перенос целой папки в Корзину использует `plan_add_directory(scanId, directoryId)` и тот же подтверждённый план. После удаления выбранных файлов запрос пересчитывает размеры всех предков; directoryId сохраняется до нового сканирования.

Карта и список используют одну ограниченную страницу. Выбор с карты подсвечивает соответствующую строку; выбор из списка подсвечивает прямоугольник. Для папок доступны переход внутрь, показ в файловом менеджере и подтверждённый перенос целиком в Корзину, для файлов — открытие, показ и подтверждённый перенос в Корзину.

## Обмен с оболочкой

Имена команд собраны в src-tauri/build.rs и явном разрешении commands.toml. Граница frontend/Rust описана в src/types.ts. Общих разрешений для файловой системы, оболочки или произвольного системного открытия в JavaScript нет. Плагин открытия вызывается только из Rust после проверки файловой записи.

Статус опрашивается раз в 500 мс только во время активной задачи. Запросы вида объединяются, а ответы устаревшего поколения игнорируются. Для изменения файлов используется отдельная сериализованная цепочка действий интерфейса, но окончательные проверки остаются в Engine.

## Удаление

План содержит fileId и снимки явно выбранных каталогов с монотонной planRevision. Всего разрешено до 10 000 объектов с учётом вложенных файлов и каталогов. Родительский пункт заменяет дочерние пункты и уже добавленные файлы: один объект не переносится дважды. Снимок каталога включает идентичность всех каталогов и fingerprint каждого файла. Проверка полного поддерева отклоняет неизвестные, пропущенные, изменённые и исчезнувшие объекты; ссылки не обходятся. Метаданные проверяются вне блокировки индекса, под общим mutation-замком и вне потока интерфейса. Страница плана содержит не более 200 пунктов: сначала папки, затем файлы. Подтверждение содержит ревизию увиденного пользователем плана. Backend отклоняет устаревшее подтверждение. Перед каждым вызовом ОС: проверка → синхронная запись намерения в журнал → повторная проверка → Корзина → запись результата. Неуспешный пункт остаётся в плане. Никаких фоновых повторных попыток после перезапуска нет.

Windows использует отдельный небольшой модуль COM с явным FOFX_RECYCLEONDELETE и запретом связанного перемещения HTML-папок. Linux использует GIO trash, macOS — адаптер trash. Единственный разрешённый unsafe-код самого проекта находится в модуле Windows COM и документирует время жизни буфера и COM-потока. Остальные модули запрещают unsafe на уровне предупреждения deny.

## Почему без React, PixiJS и базы

При таком количестве экранов отдельная система компонентов и хранилище состояния увеличили бы объём связующего кода. Ограниченной страницы из 200 элементов достаточно для DOM-карты; геометрия и браузерные сценарии проверяются тестами. Производительность на очень больших реальных каталогах отдельно не измерялась. SQLite, постоянный индекс и наблюдатель файловой системы не нужны для одного явно выбранного сеанса уборки.
